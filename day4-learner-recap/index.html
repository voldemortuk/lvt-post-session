What We Covered

Three parts, one closing question.

Day 3 was about not trusting AI-written code until it earned it. Day 4 zoomed out: what you're actually building around the model (the harness), how far you can push that from one agent to a fleet (orchestration), and what any of this costs you once it's running in production, not just while it's shipping.

01

Agent Harness

The scaffolding you build around the model — and why it's not optional

  • The big idea: Agent = Model + Harness. If you're not the model, you're the harness — prompts, tools, infrastructure, and control logic, treated as a real artifact: designed, versioned, and reviewed like any other system. It tightens every time the agent slips; each failure becomes a new rule, guardrail, or check.
  • What the harness includes: prompts & agent files (system prompts, CLAUDE.md, AGENTS.md, skill files, subagent prompts), tools & MCP servers, bundled infrastructure (filesystem, sandbox, browser), orchestration logic (subagent spawning, handoffs, model routing), hooks & middleware (deterministic execution — compaction, continuation, lint checks), and observability (logs, traces, cost, latency).
  • Why models need a harness at all: out of the box, models can't maintain durable state across interactions, can't execute the code they write, can't access realtime knowledge beyond training data, and can't set up their own environments. The harness carries all of that.
  • Most production agent failures come from the harness, not the model — context rot, tool overload, brittle tool wiring, latency, irrelevant material, weak verification, and missing guardrails are the common failure modes teams actually hit.
  • The blueprint for an effective harness: context engineering & management, tool orchestration & guardrails, human-in-the-loop (HITL) controls, and lifecycle & state management.

The harness, end to end: context goes in, the model reasons and decides, and everything else — control, action, persistence, verification — is scaffolding around it.

Every harness feature is a bridge across a specific thing the model can't do on its own.

02

Agent Orchestration

From one agent to a fleet — subagents, agent teams & dynamic workflows

  • Conductor vs. Orchestrator: a conductor steers one agent synchronously, in the loop the whole time — pair programming, leveled up. An orchestrator writes the brief once; the fleet clones, branches, codes, tests, and hands back a PR. Effort front-loads onto the spec and back-loads onto review; the middle runs itself. ~90% of engineers already use AI to write code — the frontier isn't one assistant anymore, it's a fleet.
  • SubAgents vs. Agent Teams — the two multi-agent patterns, compared directly: subagents own their context but report results back to the main agent only, with the main agent managing all work (lower token cost, best for focused tasks where only the result matters). Agent teams are fully independent, message each other directly, and self-coordinate via a shared task list (higher token cost, best for work that needs discussion and collaboration). Agent teams are switched on with CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1.
  • Dynamic Workflows move the plan out of the conversation and into a rerunnable script Claude writes — for codebase audits, large migrations, and cross-checked research, at a scale (dozens to hundreds of agents) no single conversation can coordinate turn by turn.
  • The Factory Model: plan (write specs with acceptance criteria — your spec is the leverage) → spawn (create the team) → monitor (check in every 5–10 minutes, don't hover) → verify (verification is the bottleneck, not generation) → integrate (merge, resolve conflicts) → retro (update AGENTS.md — compound learning). Practical limits that keep it running: 3–5 agents as a WIP sweet spot, a kill criterion (stuck 3+ iterations on the same error → stop and reassign), and one file, one owner — never let two agents edit the same file.
  • Five patterns to start today: subagents for decomposition (zero setup, start here), agent teams for parallelism (lead + 3 teammates via the shared task list), git worktrees for isolation (no merge conflicts), quality gates for trust (plan approval on risky changes, hooks that run tests on completion), and AGENTS.md for compound learning (every session reads it and updates it).
03

Economies of AI Development

Shipping fast is the cheap part — running it is where the money goes

  • The reframe: the entire AI pitch is velocity, but speed was never the expensive part. The number that matters is Total Cost of Ownership — not how fast you shipped, but what it costs to keep it alive. CapEx is the one-time upfront cost to build; OpEx is the ongoing cost to run, and it never stops. The shift nobody budgeted for: in AI-assisted work, OpEx is now a token bill.
  • Vibe coding's hidden debt (low CapEx, high OpEx): token burn (dumping huge files into context creates a prompting loop — every retry burns tokens), a maintenance tax (ad-hoc prompts produce unstructured code; six months on, an engineer spends days reverse-engineering it to fix one bug), and security remediation (fast code generation means fast vulnerability generation, and a flaw caught in production costs exponentially more than one caught at design).
  • Agentic engineering's investment (high CapEx, low OpEx): design the API schemas before the code, build deterministic test suites so output gets checked not trusted, and structure the agent's context — the one that matters most. The payoff: the marginal cost of every feature after that drops off a cliff.
  • Three levers that actually move the bill: a tight payload (CLAUDE.md plus only the files a task touches, not the whole repo — the big one), dynamic context (skills and tool calling, MCP servers, pulling context on demand instead of carrying it all), and intelligent model routing (heavy models for requirements/architecture/first implementation, small cheap models for tests/review/CI — same output quality, a fraction of the cost).
  • AI amplifies whatever culture it lands in — it doesn't fix your engineering culture, it scales it, in both directions. For builders: write AGENTS.md first and grow it, put tests and evals before the code. For leaders: the eval is the bar, not the demo — gate shipping on eval coverage the way you gate deployment on test coverage. For organizations: fund the harness as engineering investment, not overhead — skip the scaffolding and you buy speed without quality, debt that compounds.
Check Your Understanding

The one question from the room.

Day 4 didn't run a scored quiz like the earlier days — this was the session's own live discussion check instead, put here properly since the deck's own "answer" slide was left blank for the instructor to take live.

Who can explain the difference between an agent, a model, and a harness?
The model is the one piece that reasons and decides — that's all it does natively, and it's the only part that's actually "AI." The harness is everything built around it: the prompts and context you feed in, the tools and MCPs it can call, the control logic that directs it (compaction, orchestration, ralph loops), where it persists state (filesystem, git), and how its work gets observed and verified (test runs, logs, screenshots). The agent is the two together — model plus harness, shipped as one system. The line from today's deck: if you're not the model, you're the harness.
Key Takeaways

If you remember six things.

If you're not the model, you're the harness

Prompts, tools, infrastructure, and control logic are a real system — designed, versioned, and reviewed, not an afterthought around the model.

Most agent failures come from the harness, not the model

Context rot, tool overload, brittle wiring, and missing guardrails are the failure modes that actually show up in production.

Subagents report back; teammates talk to each other

That single architectural difference is what decides token cost and what kind of work each pattern is actually good for.

Verification is the bottleneck, not generation

In the Factory Model, the human's job shifts from writing code to writing specs and checking output — that's where the real time goes now.

Context is a line item, not a technical detail

A tight payload, dynamic context, and model routing are the three levers that actually move a token bill — and they compound.

AI scales your culture, it doesn't fix it

Good engineering discipline gets amplified by AI. So does bad discipline. The harness is what decides which one you get.

Questions We Parked or Rushed

The answers we owed you.

Five questions, properly answered — some got a fast live answer worth writing down cleanly, the rest genuinely didn't get one on the day.

Is Claude Code's “rules” folder something we're covering today — what do you actually use it for?
This got set aside for time during the session, so here's the proper answer. .claude/rules/ is a real, current part of the .claude directory, separate from the single CLAUDE.md file: topic-scoped instruction files instead of one growing document. A rule with no paths: frontmatter loads at session start, same as CLAUDE.md. A rule with paths: frontmatter only loads when Claude actually reads a matching file — so you can scope a convention to, say, just your frontend or just your test files, and it costs nothing on unrelated tasks. The trigger to reach for it: once CLAUDE.md creeps past roughly 200 lines, start moving sections into rules instead of letting one file keep growing. Like CLAUDE.md, a rule is guidance Claude reads, not something Claude Code enforces — for guaranteed behavior, that's still hooks or permissions.
As everything changes so rapidly, how do you stay on top of the latest changes?
Claude Code ships a proper changelog at code.claude.com/docs/en/changelog — every release, timestamped, with its new features, improvements, and fixes listed in order. That's the single fastest way to know what shipped and when, and it's worth bookmarking over any secondhand summary. The rest of the docs reinforce it: pages are actively version-tagged against specific releases (you'll see notes like “as of v2.1.199” throughout this very recap's own citations), so a page read months ago may already be stale on one specific behavior even if the general concept still holds — check the version tag, not just the topic.
Any ideas or resources for applying this to Product Management?
Three pieces of today's content carry over to product work directly. The Factory Model's Plan step — writing specs with acceptance criteria before any agent is spawned — is a PM's actual leverage point, not an engineering-only habit. The Leaders playbook's “the eval is the bar, not the demo” framing gives you a rubric to hold a feature to, the same way an engineering team gates a release on test coverage. And the CapEx/OpEx/TCO framing from Part 3 is ready-made vocabulary for prioritization conversations that go beyond “how fast can we ship this.” The room's own PM landed on a similar read live: Ash Roberts named the agent-orchestration portion specifically, seeing real potential for building agents around discovery, market research, and pricing work.
What's the actual advantage of running a code reviewer as a subagent instead of a skill?
A skill runs inside your existing session, using the same context window, which makes it the cheaper option for smaller, focused tasks. A subagent spins up its own disposable context window instead — it reads the code, does the review, works through everything on its own, and sends back only a summary. That costs more tokens for the separate instance, but your main conversation never has to hold the reviewed files itself. One practical wrinkle: which of the two actually runs depends on how you phrase the request — a plain prose prompt routes to the subagent automatically, but prefacing it with @code-reviewer doesn't.
What does “ultracode” actually do?
Ultracode is a session mode, not a formatter or a one-off command. Turn it on and Claude Code defaults to fanning work out across multi-agent workflows, spending tokens freely to chase the most exhaustive, verified answer instead of the fastest one. Off, it stays lean and only does that when you explicitly ask for it. Mechanically, include the keyword ultracode in a prompt, or run /effort ultracode to make it the session default, and Claude writes and runs a dynamic workflow for that task instead of working through it turn by turn. Toggle it via /config → Dynamic workflows; if it triggers by accident, Option+W (Mac) or Alt+W (Windows/Linux) right after typing dismisses it.
