Part A · Multiple Choice

Questions 1–10, one correct answer each.

Every question has exactly one correct answer. Pick the single best option.

Q1

An engineer skips planning and tells the agent to start coding. The first version arrives in minutes. Fixing the approach then takes two hours.

In Explore → Plan → Code → Commit, why is Plan the best place to catch a problem?

  • Plan is the only step where the agent reads the codebase.
  • Plan gives you a written record, so mistakes are easier to trace later.
  • Fixing a wrong approach is cheap before code exists and expensive after. ✓
  • Once you approve a plan, the agent stops making mistakes.

Nothing has been built yet. Changing a sentence in the plan costs nothing. Change the same decision later and you rewrite the code, the tests, and every file around them. That's why the workflow puts thinking before doing — Plan is the cheapest place to course correct.

Explore reads the code too, so that's not what makes Plan the answer. The written-record option names a real benefit, but not the right reason — a plan being easier to trace isn't what makes it the best place to catch a problem. And approving a plan reduces mistakes, it doesn't remove them or replace the review that follows.

Q2

You spend an hour debugging authentication. The bug is fixed and the ticket is closed. Your next task is a reporting feature. It touches none of the same code.

What should you do before you start?

  • Run /compact, so a summary of the auth work stays available.
  • Run /clear, because unrelated history biases the new task. ✓
  • Run /context, so you can see how much space the auth work is using.
  • Nothing. Automatic compaction drops the auth work once the window fills.

/clear wipes the session entirely, so you begin with a clean slate — the rule for switching to unrelated work. The auth work is finished; keeping it adds no value, and it biases the new task. Your CLAUDE.md stays loaded, so project conventions survive the reset.

/compact is the right command for a different situation — it summarizes and continues, and you're not continuing here. /context is real, but it only reports usage; it frees nothing. And automatic compaction summarizes the conversation to free space — it doesn't delete work you've already finished.

Q3

A team runs Claude review jobs on every pull request. On one request, the security review posts a high severity finding. Every other check is green. The pull request merges anyway — no check blocks it.

Why did the finding not stop the merge?

  • The review job failed to start, so its result never counted.
  • High severity findings block a merge only after a second reviewer agrees.
  • The job marked the finding as a false positive, so it reported success.
  • Review jobs post findings and exit clean. Only deterministic checks block a merge. ✓

Claude review jobs advise. They post findings and exit clean, so severity never fails a build. Four deterministic checks block a merge: lint, type check, tests, and the secret scan. A review comment is a claim; a failing test is proof. If you want a finding to block, write the assertion and move it into the test suite.

The job did run and did post its finding, so that's not it. There's no such approval rule requiring a second reviewer. And the job exits clean whether the finding is real or a false positive — that's the whole point of it advising rather than blocking.

Q4

A teammate says: “Plan Mode is slower. The agent writes the code twice, once for the plan and once for real.”

How would you correct that?

  • Plan Mode writes no code. The agent reads, searches, and asks questions, but changes nothing. ✓
  • Plan Mode writes the code, then discards it unless you approve.
  • Plan Mode asks permission before each edit, so you approve every change.
  • Plan Mode is auto accept with the diff shown first.

Plan Mode is a read-only operating mode, not a rehearsal. The agent reads files, searches the codebase, lists directories, and asks clarifying questions. It cannot write files or run shell commands. The output is a reviewable plan — nothing is implemented until you approve it.

Nothing gets written and discarded — that step doesn't exist. Asking permission before each edit describes Normal Mode. Auto-accept with the diff shown first describes Auto Accept Mode. Both are real modes; neither is Plan Mode.

Q5

A team wants the formatter to run after every file edit. They wrote that rule into their CLAUDE.md. It usually runs. Sometimes it does not.

What is the right fix?

  • Repeat the rule in every prompt so the model always sees it.
  • Add a PostToolUse hook. A hook runs every time, whatever the model decides. ✓
  • Move the rule into a SKILL.md so it loads on every edit.
  • Switch to a stronger model that follows rules more reliably.

Asking is not the same as guaranteeing. The model reads a written rule and then decides, so “most of the time” is the best a rule can offer. A hook is deterministic — it always runs. The edit fires the event and the command runs, every time, and it costs zero tokens since it runs outside the context window.

Repeating the rule in every prompt or switching models still relies on the model choosing to follow a request — a request is not a guarantee. Moving it into a skill has the same flaw, and it's also wrong about skills specifically: a skill loads only when your request matches its description, not on every edit.

Q6

A project has six MCP servers connected. Most belong to other projects. Nobody has used them this week. The context window fills up before anyone sends a message.

What explains this?

  • Each server loads its tool definitions into context, even when nobody uses them. ✓
  • Each server runs a background process that consumes memory on the machine.
  • Connected servers call their tools automatically on every prompt.
  • Connected servers append their configuration to CLAUDE.md.

An MCP server loads its tool definitions into context up front — they take up space whether you call the tools or not. Run /mcp to see what's connected and turn off the servers this task doesn't need. A CLI is cheaper. So is a skill, which keeps only its name and description in context until it matches.

That's machine memory, not the context window. Tools only run when Claude decides to call them, not automatically. And MCP servers don't write to your project memory file — that mechanism doesn't exist.

Q7

The agent reports that the test suite is green. You open the new test. It calls the function once. The only check is that the call did not throw an error. Nothing checks the value it returns.

How should you treat this test?

  • As green. It passes, so the function works.
  • Delete it, so the suite shows real coverage.
  • Leave it. The security review will find the bug.
  • As red. Strengthen the assertion and run it again. ✓

A green test that asserts nothing is red. It passes no matter what the function returns, so it hides every defect inside that function. Fix the cause, then run the gate again — don't report success on a gate that never checked anything.

Treating it as green is the mistake itself: the signal looks good because it's green, not because it tested anything. Deleting it removes the warning but leaves the behavior uncovered. And a correctness problem isn't what a security review is looking for.

Q8

A team reviews a new skill before installing it. The skill can read the project's .env file. It also reads text from public issue comments. And it can post to any URL on the internet.

Why is this combination dangerous?

  • Together, untrusted text can tell the skill to send private data out. ✓
  • Any skill that reads a .env file is unsafe, whatever else it does.
  • Reading public issue comments slows the skill down.
  • Posting to a URL is unsafe only when the skill also writes files.

This is the lethal trifecta. A skill is dangerous when it has all three at once: it reads private data (SSH keys, API tokens, .env), it sees untrusted content (a web page, an email, an issue comment), and it can reach the outside (network egress, a webhook, curl). Any one alone is fine — all three together let a stranger's text act as an instruction, and your secrets can then leave the network. Break the chain by removing any one of the three.

Plenty of safe skills read a .env file — the combination is the risk, not the single capability. Reading issue comments is a performance question at worst, not a security one. And writing files isn't part of the trifecta at all.

Q9

Your team is choosing between subagents and an agent team for the same piece of work.

Which statement about their token cost is correct?

  • Subagents cost more, because each one returns a full transcript to the main agent.
  • Agent teams cost more, because each teammate is a separate Claude instance. ✓
  • They cost the same. Both run inside the main session's context window.
  • Agent teams cost less, because they work in parallel and finish in fewer turns.

A subagent works, then returns a short summary — your main context absorbs only the result, so the cost stays lower. An agent team runs several full sessions at once; each teammate is a separate Claude instance with its own context window. More instances, more tokens. Teams earn that cost on work that needs discussion; they waste it on focused tasks where only the result matters.

That's backward — a subagent discards its transcript and returns a summary, it doesn't return the full thing. Both give workers their own context window, so they don't cost the same. And running in parallel finishes sooner, but every teammate still spends its own tokens — speed and cost aren't the same axis.

Q10

A team sends every request to the largest available model. Architecture decisions go there. So do typo fixes, routine test generation, and CI checks. The monthly bill is far higher than the team expected. The work itself is fine.

What explains the bill?

  • The largest model charges a flat monthly fee for each seat on the team.
  • Architecture decisions consume most of the tokens the team spends.
  • Routine work is billed at frontier prices, though a smaller model would match the quality. ✓
  • CI checks retry until they pass, which multiplies the cost of every run.

This is a routing problem. Big models are worth the cost on the hard thinking — requirements, architecture, first implementation. Tests, review, and CI monitoring are deterministic grunt work; a small, fast, cheap model does that work at the same output quality for a fraction of the tokens. This team pays frontier prices for all of it. That gap is the bill.

Tokens are metered, not sold per seat. Architecture is a small share of requests — and it's also the one place the large model is actually worth its cost. There's no retry loop described here to multiply anything.

Part B · Subjective Questions

Answer both, in your own words.

Cover every point listed under "Think about" — these are scenario-based, not multiple choice.

Subjective 1

Scenario: A teammate opens a pull request that an agent wrote. The code is clean. It matches the house style. The whole suite is green. You have thirty minutes to decide whether it ships.

Explain how you decide whether to trust this change, and where you spend your review time.

Think about
  • Why code that looks idiomatic can still be wrong, and why that makes review harder.
  • What the change should have passed before you ever saw the diff.
  • How you treat a passing test that asserts nothing.
  • Why a reviewer who did not write the code catches what the author cannot.
  • Which checks belong to a machine, and which need your judgment.
Subjective 2

Scenario: Your team runs agents on most tasks. Runs are slow and expensive. Results vary between engineers. Last week two agents edited the same file in one run and undid each other's work.

Explain what you change, and why cost and reliability improve together instead of trading off.

Think about
  • What the harness is, and why these are harness problems, not model problems.
  • Why context is a cost line item, and how to send less but better context.
  • Where a large model is worth the cost, and where a smaller one is enough.
  • How to stop two agents from editing the same file, and how many to run at once.
  • One practice that makes each run smarter than the last.
